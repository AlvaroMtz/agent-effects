# Migrating from 0.0.1 to 0.0.2

`0.0.2` hardens the core contract before replay and JSONL persistence arrive.
Four changes are breaking. All four are mechanical, and each exists because
`0.0.1` shipped a contract that could not support what `0.0.3` has to do.

## 1. Executors return an outcome, not a result

An executor no longer names the effect its result belongs to. It reports what
the outside world did; the runtime owns identity (ADR-0011).

**Before**

```ts
const executor: EffectExecutor = {
  async execute(effect) {
    return { effectId: effect.id, status: "ok", output: { temperature: 20 } };
  },
};
```

**After**

```ts
const executor: EffectExecutor = {
  async execute(effect) {
    return { status: "ok", output: { temperature: 20 } };
  },
};
```

An executor can return only `ok` or `error`. If yours returned `pending`,
`cancelled` or `denied`, there was no lifecycle able to resolve them: the effect
was recorded as requested and never resolved, and resolving it again was
rejected as a duplicate. Those states remain in `EffectResult` for consumers.

## 2. Journal lookups take a run

```ts
// before
await journal.findResult("fx_1");

// after
await journal.findResult("run_1", "fx_1");
```

Identity is unique within a run, not globally (ADR-0002), so one journal can
hold many runs. The `0.0.1` "one journal instance per run" convention is gone;
delete any code that existed to honor it.

## 3. Request entries carry the whole effect

```ts
// before
{ kind: "effect.requested", runId: "run_1", effectId: "fx_1" }

// after
{
  kind: "effect.requested",
  runId: "run_1",
  effect: {
    id: "fx_1",
    runId: "run_1",
    type: "tool.invoke",
    input: { tool: "weather", arguments: { city: "Madrid" } },
  },
}
```

The entry's `runId` must equal `effect.runId`; a mismatch is rejected with the
`run-id-mismatch` invariant code. Custom journal backends must persist the
effect, not just its id, or replay cannot verify what was attempted (ADR-0012).

## 4. Effect input and result output are `JsonValue`

`Effect<TInput extends JsonValue>` and `EffectResultOk.output: JsonValue`. The
specification always forbade functions, promises, class instances, sockets and
connections in the portable contract; now the type enforces it.

If you declared an input shape as an `interface`, change it to a `type` alias.
Only aliases carry the implicit index signature that makes an object type
assignable to `JsonValue` — this is a TypeScript rule, not a style preference:

```ts
// before — not assignable to JsonValue
interface MyInput { tool: string; arguments: JsonValue }

// after
type MyInput = { tool: string; arguments: JsonValue };
```

## Also new, not breaking

- **Journals snapshot on write and on read.** A backend stores a deep copy and
  returns deep copies, so recorded history cannot be mutated through a shared
  reference. If you relied on reading an entry and editing it in place, that was
  never append-only; append a correction instead.
- **An occurrence resolves at most once.** A second `effect.resolved` for the
  same `(runId, effectId)` is rejected with `duplicate-resolution`.
- **`JournalInvariantCode`** is exported, covering `duplicate-effect-id`,
  `missing-request`, `duplicate-resolution` and `run-id-mismatch`.

## Unchanged on purpose

- The six resolution states, and `unknown` as the answer when the executor
  completed but the result could not be recorded.
- `SerializableError`: a stable `code`, a `message`, optional `details` and an
  advisory `retryable`. No `stack` field — a journal is sensitive by default,
  and execution traces do not belong in one.
- Exactly two dispatchable effect kinds, `tool.invoke` and `model.invoke`.
